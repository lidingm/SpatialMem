# SpatialMem：训练时自进化的空间推理 Agent

> 面向 VSIBench，用 VLM Planner + 可执行 SKILL 库 + 陈述性 Memory + 4 条自进化路径。训练时积累知识，测试时消费知识。

---

## 一、动机：现有工作留下了什么空隙

空间推理是 VLM 的短板。近期两个 agent 方向的工作各有优势也各有边界：

| 工作 | 做了什么 | 局限 |
|---|---|---|
| **S-Agent** (arxiv 2606.20515) | 用 Planner 编排 3 级空间工具（2D→3D→专家），维护 Scene Memory + Agent Memory | 两类记忆都是 **per-episode**（同一场景内），跨样本不积累任何东西 |
| **SpatialClaw** (arxiv 2606.13673) | 每个问题起一个持久 Jupyter Kernel，让 VLM 迭代写 Python cell | 每次从零开始，**完全无记忆** |

**SpatialMem 的位置**：把 SKILL 库 + Memory 先验做成**跨样本的、训练时不断进化**的两类持久化知识。用训练集当作"积累经验"的场地，测试时用进化后的库直接检索复用。

**独有贡献**（和上面两条工作正交）：
1. **失败驱动的推理轨迹重组**：答错时 Reflector 诊断失败原因、提出修正方案、**用同一样本再跑一次做验证**，只有真验证通过的诊断才蒸馏进 SKILL 的 Known Pitfalls。这条闭环让 SKILL 库不会被幻觉污染。
2. **4 条自进化路径把每个训练样本都变成信号**：无论答对答错、无论用没用 SKILL，都有对应的更新动作。

## 二、核心概念区分

代码里两类持久化知识严格分开，术语不能混：

| | Memory（陈述性） | SKILL（过程性） |
|---|---|---|
| 是什么 | "关于世界的事实" | "如何完成任务的过程" |
| 存储形式 | JSON | 文件夹（SKILL.md + execute.py + trajectories.jsonl） |
| 内容 | 物体尺寸先验、场景尺度先验、疑难样本记录 | 参数化的工具调用序列 |
| 迭代术语 | **更新（update）** | **进化（evolve）** |
| 迭代方式 | Welford 在线均值方差 → 单调量变 | 生成新草案、追加 pitfall、改写描述、pending 晋升 → 结构性变化 |
| 代码位置 | `agent/memory.py` | `agent/skill_lib.py` + `agent/evolve.py` |

用户和 LLM 都要遵守这个术语约定，否则论文里 ablation 描述会含糊。

## 三、整体架构

### 5 层组件

```
[5] train_vsitrain10k.py   # 多样本训练/评估驱动 + 触发 4 路径 evolve（--ckpt 指定检查点）
[4] orchestrator.py        # 单样本主循环（run / run_with_plan）
[3] Planner + Reasoner     # 3 个 VLM 角色（负责决策与格式化）
    + Reflector
[2] Memory + SkillLib      # 两类持久化知识（进化和更新的对象）
[1] ToolRegistry           # 10 个底层空间工具（DA3 / SAM3 / 代码计算）
```

### 单样本推理流

```
                          ┌─── Sample ───┐
                                  │
                                  ▼
                     ┌────── Planner (VLM) ──────┐
                     │  检索 SKILL 库 (top-k)     │
                     │  检索 Memory 上下文       │
                     │  输出 JSON plan：         │
                     │    chosen_skill / null    │
                     │    skill_params           │
                     │    raw_tool plan          │
                     └───┬────────────────┬──────┘
                         │                │
              chosen_skill               │ chosen_skill == null
                         ▼                ▼
              ┌──── SkillLib ────┐   ┌───── 原始工具循环 ─────┐
              │  invoke SKILL    │   │  Reasoner→执行→反馈    │
              │  的 execute.py   │   │  ×  MAX_ROUNDS 次      │
              └────────┬─────────┘   │  Reflector 决定继续或  │
                       │             │  终止                  │
                       │             └───────────┬────────────┘
                       └────────┬────────────────┘
                                ▼
                    Reflector.finalize (VLM)
                    按 fill/select 格式抽取答案
                                │
                                ▼
                            final answer
```

### 训练时的 4 路径自进化 + 主动 bootstrap

答完之后对比 GT，按（对/错 × 用没用 SKILL）分派：

| 结果 | 用 SKILL | 路径 | 动作 |
|---|---|---|---|
| ✅ 对 | 是 | **A** | 强化 SKILL（`success_count++`）；每 `DISTILL_TRIGGER_N` 次成功，LLM 读近 20 条轨迹摘要 → 改写 SKILL.md 的 `When to Use` |
| ✅ 对 | 否 | **B** | LLM 把轨迹蒸馏成新 SKILL 草案（生成 SKILL.md + execute.py），落到 `skills/pending/` |
| ❌ 错 | 是 | **C** | Reflector 诊断错误 → 提出修正 plan → **同样本重跑验证** → 若验证通过，LLM 提炼 pitfall 追加到 SKILL 的 `Known Pitfalls` |
| ❌ 错 | 否 | **D** | 同 C 前半段。验证通过则蒸馏为新 SKILL 草案落 pending |

**如果反思重跑没验证通过**：写入 `memory/unsolved_cases.jsonl`，**不动 SKILL 库**。这是防止 LLM 幻觉污染库的关键。

pending 里的 SKILL 满足 `success_count >= PENDING_PROMOTE_K`（默认 3）时晋升到主库，成为可被 Planner 检索的一员（每 `PROMOTE_EVERY=50` 个样本检查一次）。

**Path B 的去重机制**：`distill_new_skill` 调用时会先把该类别所有已有 SKILL（主库 + pending）展示给 LLM，让它决定：(a) `skip` — 已有 SKILL 完全覆盖，不重复创建；(b) `update` — 已有 SKILL 高度相似，把补充描述追加到其 `When to Use`；(c) `create` — 真正不同的新策略，名字需体现区别。防止在同一类别下产生大量重复 pending skill。

**Bootstrap（主动策划新 SKILL）**：Path B/D 是被动的 —— 只在单个样本恰好答对/反思成功时触发。如果某个 task_category 完全没被工具覆盖（比如 route_planning 里的连续导航决策），Path B/D 可能一直不 fire，SKILL 库对这类任务永远长不出东西。

为此加了 **`bootstrap_skill_for_category`**：

1. 每个"没匹配到 SKILL"的样本，其轨迹（含答对答错）追加到 `memory/category_trajectories/{cat}.jsonl`
2. 当某个 category 累积到 `BOOTSTRAP_TRIGGER_N=8` 个未覆盖样本，且**依然没有任何 pending 或主库 SKILL 匹配** → 触发 `bootstrap_skill_for_category`
3. LLM 读 5 条答对 + 5 条答错的轨迹对比，主动设计一个 SKILL 草案（同样 AST + runtime 校验 → save_pending）
4. 每个 category 只 bootstrap 一次（`.bootstrapped` 标记文件），失败不重试

这样框架就有了**双通道 SKILL 发现能力**：
- **Reactive (Path B/D)**: per-sample 蒸馏 —— 快，覆盖易成功的类型
- **Proactive (bootstrap)**: per-category 综合 —— 慢，兜底难覆盖的类型

Bootstrap 优先级低于 Path B/D：如果 Path B 已经从某个成功样本蒸馏出 pending SKILL，bootstrap 检测到 `retrieve()` 非空 → 跳过。避免重复产出。

## 五、SKILL 结构约定

每个 SKILL 是一个文件夹，必须包含 3 个文件。以 `skills/measure_distance/` 为例：

**SKILL.md**
```markdown
---
name: measure_distance
task_categories: [distance]
total_calls: 12
success_count: 8
failure_count: 4
success_rate: 0.6667
version: 3
seeded: true
---

# When to Use
两物体距离测量，或物体到相机距离。（本段落在成功次数够多时会被 LLM 重写）

# Parameters
- `targets` (list[str], **REQUIRED**): 至少 2 个物体名。
- `mode` (str): "object_to_object" | "object_to_camera"
- ...

# Tool Sequence
1. depth_estimation
2. object_segmentation × N
3. instance_3d_localization
4. distance_computation

# Known Pitfalls
- **[反射材质]** 玻璃/镜面导致 DA3 深度失效 → 改用 3D 重建路径
- ...（Path C 蒸馏追加，可持续增长）

# Examples
- ...
```

**execute.py**
```python
def execute(sample, tools, ctx, params=None):
    """
    - sample: SpatialSample
    - tools: ToolRegistry；用 tools.execute_tool(name, params, frame_paths) 调用
    - ctx: 共享上下文（读 ctx["frame_paths"] 拿准备好的帧）
    - params: Planner 传进来的 skill_params
    返回 {success, tool_calls, summary}
    """
```

**trajectories.jsonl**：每行一条压缩摘要（不存原始图像/数组），供 Path A 蒸馏时读取近 N 条重写 When to Use。

## 六、10 个底层工具

保留自上一版 SpatialMem，语义不变，仅路径改为 config 驱动。

**A 类：视觉生成（生成证据）**

| 工具 | 作用 |
|---|---|
| `depth_estimation` | Depth Anything 3：所有帧的 metric 深度 + 相机内外参 + 点云 |
| `object_segmentation` | SAM3 文本 prompt 分割，返回 2D mask + bbox + confidence |
| `annotation_localization` | 用样本自带标注（VSIBench 无用） |
| `bev_generation` | 从点云生成鸟瞰图 |
| `novel_view_synthesis` | 3DGS 新视角合成 |

**B 类：代码计算（精确数值）**

| 工具 | 作用 |
|---|---|
| `instance_3d_localization` | 2D mask → 3D 反投影 → 跨帧 3D 聚类合并同实例 |
| `distance_computation` | 物体间 / 物体到相机的欧式距离 |
| `direction_computation` | 从 viewpoint 观察 target 相对 reference 的方位 |
| `instance_counting` | 3D 聚类后的独立实例数 |
| `scene_size_computation` | 从点云计算房间 extent + floor area |

**⚠ 工具的磁盘副作用**：视觉生成类工具（DA3、SAM3）默认会把中间产物写到 `outputs/` 目录：

- `outputs/da3/prediction.npz`（每样本 10-50 MB，含深度+内外参）
- `outputs/da3/depth_vis/*.png`（每样本每帧一张彩色深度图，~50 KB × 10 = 500 KB）
- `outputs/da3/bev_from_depth.png`、3DGS PLY、NVS 帧（按需触发）
- `outputs/sam3/{prompt}/*.png`（每个 SAM3 分割 prompt 每帧一张可视化）
- `outputs/spatial/*.json`（3D 定位、场景尺寸的数值结果）

**跑一次完整 VSIBench 评测（4130 样本）大约会产出 ~100 GB 中间产物**。建议：

1. **把 `outputs/` 指向 scratch 盘**：`export OUTPUTS_DIR=/scratch/spatialmem_outputs` 或 `ln -s /path/to/scratch outputs`
2. **训练完后 `rm -rf outputs/`**：框架下次会懒惰重建
3. **不需要 debug 时关闭可视化**：改 `agent/tools.py::_run_depth` 里的 `save_depth_vis=True` 为 `False`（省掉最大头的深度图 PNG）

这些产物**框架本身不依赖**（SKILL/Memory 状态独立存在 `skills/`、`memory/`、`ckpts/` 里），只是用于**人工排查单次工具调用**（看深度、看分割、验证 3D 定位）。纯训练/评估可以直接把 `OUTPUTS_DIR` 指向可弃盘。

## 八、开发阶段的关键验证

**1. 全 4 路径可触发**（`scripts/debug_llm.py` mock 掉 DA3/SAM3 跑真样本）：
- Path A：判断类 SKILL 成功后 pit_len 从 9 增长到 485 字符（追加 2 条 pitfall）
- Path B：`object_size_estimation`/`route_planning` 这类无 seed 的类型，成功轨迹被蒸馏成 pending SKILL
- Path C：Reflector 诊断参数填错→重跑修正 plan 验证通过→pitfall 精确对应错误："Using 'standing by the lamp' as a reference instead of 'pillow' → always use the observer's facing object as the reference"
- Path D：无 seed 且答错的样本，反思失败则写 unsolved_cases

**2. 小模型能驱动整个架构**：`qwen3-vl-30b-a3b-instruct`（MoE，3B active，等效算力≈8B）跑下来：

| 指标 | gpt-4o-mini | qwen3-vl-30b-a3b |
|---|---|---|
| SKILL 命中率 | 73% | **76%** |
| Path A 触发率 | 23% | 24% |
| JSON 解析失败率 | 7% | 6% |
| 蒸馏 pitfall 长度 | +185 chars | **+485 chars（更精确）** |

**结论**：架构不依赖大模型独特能力。这对论文的 SFT 蒸馏方向（例如做一个 SpatialMem-8B）扫清了障碍。

**3. 迭代中发现并修复的 6 个 bug**（均记录在 `docs/design.md`）：
1. Planner 把 tool 名当 SKILL 名 → prompt 强调约束
2. `distill_new_skill` 生成的 execute.py 有嵌套 def + 错误 API 假设 → prompt 改约 + AST 校验 + 防御性剥离
3. SKILL 静默跳过必需步骤 → 每个 SKILL execute.py 加参数校验
4. **Planner 看不到 SKILL Parameters**（影响最大）→ `Skill.brief()` 展示 Parameters + Pitfalls 段落
5. viewpoint 描述短语污染 Memory → `_update_memory_from_tools` 过滤 >3 词的 label
6. 工具失败 traceback 刷屏 → 默认静默，`SPATIALMEM_DEBUG_TRACES=1` 打开

Notebook 里的入口代码模式：

```python
from agent.config import ensure_dirs
from agent.data_loader import VSIBenchDataLoader
from agent.llm_client import LLMClient
from agent.memory import Memory
from agent.orchestrator import Orchestrator
from agent.planner import Planner
from agent.reasoner import Reasoner
from agent.reflector import Reflector
from agent.skill_lib import SkillLib
from agent.tools import ToolRegistry
from agent.train_loop import TrainLoop

from your_tool_wrappers import da3_tool, sam3_tool

ensure_dirs()

llm       = LLMClient(base_url=..., api_key=..., model=...)
loader    = VSIBenchDataLoader()
memory    = Memory()
skill_lib = SkillLib()
tools     = ToolRegistry(da3_tool=da3_tool, sam3_tool=sam3_tool)
planner   = Planner(llm)
reasoner  = Reasoner(llm)
reflector = Reflector(llm)

orch = Orchestrator(tools, memory, skill_lib, planner, reasoner, reflector)
tl   = TrainLoop(orch, loader, memory, skill_lib, reflector, llm)

# 训练：进化 SKILL + Memory
tl.run_task_type("object_abs_distance", max_samples=50, evolve=True)

# 评估：冻结库，测精度
tl.run_task_type("object_abs_distance", max_samples=50, evolve=False,
                 save_name="object_abs_distance_test")
```

## 十、可调节超参（`agent/config.py`）

| 常量 | 默认 | 含义 |
|---|---|---|
| `MAX_FRAMES_PER_SAMPLE` | 32 | VSI 每场景 32 帧，全部使用 |
| `MAX_ROUNDS` | 3 | 原始工具循环最多反思几次 |
| `CONFIDENCE_THRESHOLD` | 0.8 | Reflector 提前 terminate 阈值 |
| `WARMUP_N` | 5 | 数值先验从 candidates 晋升到主库需要的观测数 |
| `DISTILL_TRIGGER_N` | 5 | 每几次 SKILL 成功触发一次 `distill_success` |
| `DISTILL_WINDOW` | 20 | 蒸馏时读多少条最近轨迹摘要 |
| `PENDING_PROMOTE_K` | 3 | pending SKILL 需要几次成功复用才晋升 |
| `REFLECT_MAX_ATTEMPTS` | 1 | 每个答错样本尝试重构验证几次 |

## 十一、和论文思想的对应

**核心卖点（一句话）**：*Training-time trajectory-based self-evolution of SKILLs and Memory for spatial reasoning*。

**独有技术贡献**：
1. 失败驱动的推理轨迹重组 + 重跑验证闭环（Path C/D）—— 别的工作要么只强化成功（Voyager）、要么只存反思不重构（Reflexion）、要么无跨样本记忆（S-Agent/SpatialClaw）
2. SKILL 文件夹格式（SKILL.md + execute.py）+ 版本化 + pending 晋升机制 —— 让"记忆"变成"可执行技能"
3. Memory 与 SKILL 严格分开（陈述 vs 过程，更新 vs 进化）—— 论文 ablation 时能干净拆分

**Ablation 建议**（论文实验章节）：
- Baseline：`skill_lib.retrieve(top_k=0)` + Memory 不检索 → 纯原始工具循环
- +Memory：仅注入数值先验
- +seeded SKILLs：加入 4 个手写种子
- +evolution（Path A only）：只强化，不生成新 SKILL
- +full 4-path evolution：完整自进化

期望看到 SKILL 命中率、平均工具调用轮数、准确率随累积样本数演化的曲线 —— 展示"越训越好"。

## 十二、常见问题

**Q：为什么放弃了原来的 4 角色框架（Planner/Executor/Reflector/Summarizer）？**
A：Reasoner 就是原来的 Executor + per-step LLM，`Reflector.finalize` 就是原来的 Summarizer。角色越多，ablation 越难做，也没有实质区别。

**Q：SKILL 用文件夹形式而不是 JSON，是不是过度设计？**
A：SKILL 需要既包含"何时用"（陈述性描述，供 LLM 阅读）又包含"如何用"（可执行代码）。用 markdown + py 天然分离且可读。JSON 会把两者压扁成难维护的结构。

**Q：`_template/` 是干嘛的？**
A：为了让 Path B/D 生成新 SKILL 时有一致的骨架，避免每次生成的格式漂移。目前 `distill_new_skill` 直接生成完整 SKILL.md + execute.py，未来可能改为基于模板填空。

**Q：Memory 里的 candidates 和 objects 有什么区别？**
A：candidates 是"观察次数不足以形成稳定先验"的暂存池，等 count >= WARMUP_N 才晋升到主池 objects。防止一次异常观测污染主先验。

**Q：为什么反思重构要重跑一次而不是直接信任 LLM 的诊断？**
A：LLM 反思很容易 post-hoc rationalization —— 编一个听起来合理的失败原因。让它把诊断变成"具体修正 plan → 同一样本重跑 → 看 GT 是否匹配"，才是可验证的信号。这是本框架防止 SKILL 库被污染的核心机制。
