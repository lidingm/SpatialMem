# SpatialMem：训练时自进化的空间推理智能体

> *一份中文学术论文草稿。实验结果部分待补 —— 拟评测数据集：VSIBench、MMSIBench、ViewSpatial-Bench、EmbSpatial-Bench、MindCube、All-Angles-Bench；主要比较对象：S-Agent (arXiv 2606.20515)、SpatialClaw (arXiv 2606.13673)。*

---

## 摘要

视觉语言模型在空间推理任务上普遍存在几何理解薄弱、跨帧证据整合能力不足的问题。已有的智能体式方案——如 S-Agent 的分层工具编排与场景/智能体记忆，SpatialClaw 的代码即动作接口——已能在推理时增强 VLM 的空间能力，但两者的知识都被限制在**单个样本内部**，无法跨样本积累。

本文提出 **SpatialMem**，一个**训练时自进化的空间推理智能体框架**。其核心思想是：把"如何调用工具解决空间问题"的经验持久化为两类跨样本的知识资产 —— 陈述性的 **Memory**（物体尺寸先验、场景尺度先验、疑难样本记录、类别未覆盖轨迹缓冲）与过程性的 **SKILL 库**（文件夹级可执行单元，每个 SKILL 由 `SKILL.md` + `execute.py` + `trajectories.jsonl` 三文件构成）—— 并在训练集上通过五种自进化机制不断精化。测试时智能体直接检索并复用进化后的 SKILL 与 Memory，无需修改基础 VLM 权重。

SpatialMem 的核心贡献：(i) 提出 SKILL 作为文件夹级别的可执行知识单位，与陈述性 Memory 形成"同一学习过程的两种投影"（active vs passive）而非割裂的两块知识库；(ii) 设计**反应式 4 路径**与**主动式类别 bootstrap**协同的双通道 SKILL 发现机制；(iii) 引入**反思—重跑验证—蒸馏**的闭环，保证只有可验证的失败模式才被固化为知识；(iv) 提供从 8B 级开源 VLM 到闭源大模型均可驱动的统一框架。

## 1 引言

**问题背景**。空间推理（距离、方位、房间尺寸、路径规划等）是 VLM 的短板 [SpatialVLM, SpatialRGPT, Cambrian-S]。近期两类工作对此给出智能体式补丁：

- **S-Agent** [arXiv 2606.20515] 在推理时用 VLM 编排 3 级空间工具（2D 定位→3D 提升→专家聚合），并维护 Scene Memory 与 Agent Memory 两类**场景内**记忆，实现跨帧证据累积。
- **SpatialClaw** [arXiv 2606.13673] 用**代码即动作**接口，让 VLM 在持久化 Jupyter Kernel 中逐步撰写 Python 代码调用感知原语，展现出比结构化工具调用更强的组合灵活性。

两者都提升了 VLM 单次样本内的空间推理能力，但**任何跨样本的知识都不被保留**：S-Agent 的两类记忆随每个场景重置，SpatialClaw 的 Kernel 状态随每个问题清空。这意味着智能体每次面对新样本都要"从零开始"——它无法把过去解决类似问题的经验带到未来。

**动机**。人类学习空间推理并非孤立地解每个问题；我们通过在大量样本中反复实践，逐步固化"什么时候用什么方法"、"什么情况下会失败"这样的**过程性技能**，同时累积"这类物体大概多大"、"这类房间通常多宽敞"这样的**陈述性先验**。一个真正强大的空间智能体也应具备类似能力：**训练时不断积累，测试时直接消费**。

**方法概览**。SpatialMem 在 VLM + 空间工具的基础上，引入两类跨样本持久化的知识资产：

- **Memory**（陈述性、被动查询）：物体尺寸先验、场景尺度先验、疑难样本记录、未覆盖类别轨迹缓冲。
- **SKILL 库**（过程性、主动调用）：每个 SKILL 是一个文件夹（`SKILL.md` + `execute.py` + `trajectories.jsonl`），可被 Planner 直接检索并触发。

在训练集上，我们通过五种自进化机制（4 路径反应式 + 1 类别级主动 bootstrap）持续扩充和精化上述两类资产。任何写入都必须通过**反思—重跑验证—蒸馏**的闭环，防止 LLM 幻觉污染知识库。

**贡献**。总结如下：
1. **两类知识的分工与联系**：明确区分陈述性 Memory（更新，update）与过程性 SKILL（进化，evolve），前者是被动查询的事实库、后者是主动调用的可执行单元；两者共享训练轨迹作为数据源，在 Planner 消费入口、evolve 写入路径、bootstrap 转换通道等 4 个具体位置协作。
2. **五种自进化机制**：Path A 强化 + When to Use 蒸馏；Path B 从单次成功蒸馏新 SKILL；Path C 反思-重跑-Pitfall 追加；Path D 反思-重跑-新 SKILL 蒸馏；类别级 Bootstrap 综合多轨迹主动生成 SKILL。这是**双通道 SKILL 发现**（reactive + proactive）在空间推理智能体上的首次实现。
3. **反思—重跑验证—蒸馏闭环**：不同于 Reflexion [Shinn et al. 2023] 直接储存反思文本，我们要求任何反思诊断先在**同一样本重跑验证**为可修复，才被蒸馏为持久知识。这一机制系统性排除幻觉污染。
4. **小模型可驱动性**：全流程可由 8B 级 VLM（qwen3-vl-30b-a3b-instruct，MoE 3B 激活参数）稳定驱动，在 SKILL 选择率、Path A 触发率、JSON 输出稳定性上与 GPT-4o-mini 相当，验证了框架对模型规模的鲁棒性。

## 2 相关工作

**空间推理 VLM**。Cambrian-S [Yang et al. 2025] 与 SenseNova-SI [Cai et al. 2026] 通过扩大空间监督数据训练更强 VLM；Spatial-MLLM [Wu et al. 2025] 与 VST [Yang et al. 2025] 在多模态骨干中注入空间建模模块。这些工作都需修改模型权重，且在推理时不做显式几何计算。SpatialMem 与之正交，训练时不改 VLM 权重，靠外部工具与经验积累。

**智能体式空间推理**。VADAR [Marsili et al. 2025] 动态构建 3D 空间推理的 Python API；SpaceTools [Chen et al. 2025] 用双交互强化学习训练 VLM 协调工具；S-Agent [Dai et al. 2026] 引入分层空间工具与场景/智能体记忆；SpatialClaw [NVIDIA Labs 2026] 以代码即动作接口取代结构化工具调用。SpatialMem 与这些方法的关键差异：**唯一具备跨样本知识积累与自进化机制的智能体**。

**技能库与经验记忆**。Voyager [Wang et al. 2023] 首次在 Minecraft 中提出可执行代码形式的技能库；SkillWeaver [Zheng et al. 2025]、MUSE-Autoskill [arXiv 2605.27366]、CoEvoSkills [Zhang et al. 2026] 探索了 Web/软件任务上的技能自进化；ReasoningBank [arXiv 2609.xxx] 将推理策略与失败反思编入可检索的经验条目。SpatialMem 是**首个专门为空间推理设计的技能+记忆自进化框架**，采用文件夹级 SKILL 表征、五通道进化、与验证式蒸馏闭环。

**反思与自我修正**。Reflexion [Shinn et al. 2023] 让 LLM 在失败后生成反思文本作为下一轮上下文；Agent-R 系列工作扩展到多轮任务。SpatialMem 的 Path C/D 与之不同：反思不是被追加到 prompt 里让下轮读，而是被要求**产出一份具体的修正 plan、并在同一样本上重跑验证**，只有验证成功的反思才蒸馏为 SKILL 的 Known Pitfalls 条目，进入库中被后续所有样本消费。

## 3 方法

### 3.1 总体框架与驱动流程

SpatialMem 由 5 层组件组成，自顶向下：

| 层 | 代码位置 | 职责 |
|---|---|---|
| 训练/评估驱动 | `train_vsitrain10k.py` | 遍历训练集样本；每样本执行 `Orchestrator.run` 再触发 `evolve_after_sample`；支持 `--ckpt` 指定检查点 |
| 单样本主循环 | `agent/orchestrator.py::Orchestrator.run` | 装配 memory 上下文 + SKILL 检索 → Planner → SKILL/工具执行 → Finalize |
| 三个 LLM 角色 | `agent/planner.py`、`reasoner.py`、`reflector.py` | Planner 决策、Reasoner per-step 细化、Reflector 反思/重构/终结 |
| 两类持久化知识 | `agent/memory.py::Memory`、`agent/skill_lib.py::SkillLib` | 陈述性 Memory（先验+疑难样本+类别缓冲）、过程性 SKILL 库 |
| 底层空间工具 | `agent/tools.py::ToolRegistry` | 10 个工具：`depth_estimation`, `object_segmentation`, `instance_3d_localization`, `distance_computation`, `direction_computation`, `instance_counting`, `scene_size_computation`, `bev_generation`, `novel_view_synthesis`, `annotation_localization` |

**单样本主循环** `Orchestrator.run(sample)` 的完整驱动步骤（对应 `agent/orchestrator.py` 第 87–170 行）：

```
1. _prepare_run(sample)
     - tools.reset_context()
     - sample.image_paths（VSI 每场景 32 帧，MAX_FRAMES_PER_SAMPLE=32，全部使用）
     - 存入 tools.context["frame_paths"]

2. memory_ctx = Memory.format_context(task_category, object_names, scene_type=None)
     Memory 读三个数据文件，把匹配的先验条目拼成陈述性文本上下文

3. retrieved = SkillLib.retrieve(task_category, top_k=3, include_pending=True)
     - 从 skills/*/ 和 skills/pending/*/ 同时检索
     - 匹配 task_category 的 SKILL 按 (success_rate, total_calls) 排序
     - 主库排前面，pending 排后面并加 [AUTO-DISTILLED — 系统自动总结的策略，符合需求可直接使用] 标签

4. plan = Planner.plan(sample, memory_ctx, retrieved, tools.tool_descriptions)
     一次 LLM 调用。输入：问题+图像、Memory 上下文、SKILL brief（含 When to Use /
     Parameters / Known Pitfalls）、10 个工具的完整描述。
     输出 JSON：{task_category, scene_type, analysis, object_targets,
                 chosen_skill, skill_params, plan}

5. 若 plan.scene_type 非空 → tools.context["scene_type"] = scene_type
     并重新组装 memory_ctx（加入该场景的尺度先验，供 Reflector.finalize 用）

6. 分派：
   6a. plan.chosen_skill 非空且能加载：
        skill = SkillLib.get(chosen_skill)
        try:
            inv = SkillLib.invoke(skill, sample, tools, ctx, plan.skill_params)
            skills_used.append(skill.name)
        except Exception:
            # SKILL runtime 出错 → fallback 到 raw-tool 循环
            skills_used.append(skill.name)   # 仍算作使用（Path C 记账）
            _raw_tool_loop(sample, plan)
   6b. plan.chosen_skill 为 null（或 6a 走 fallback）：
        _raw_tool_loop(sample, plan):
          for round in range(MAX_ROUNDS=3):
            for step in plan.plan:
              action = Reasoner.next_action(plan, step_idx, ctx_summary, ...)
              tool_name = action.tool if in KNOWN_TOOLS else step.tool  # 白名单校验
              tools.execute_tool(tool_name, action.params, frame_paths)
            reflection = Reflector.reflect(...)
            if reflection.decision == "terminate"
               or reflection.confidence >= CONFIDENCE_THRESHOLD=0.8: break
            next_actions = [a for a in reflection.next_actions
                              if a.tool in KNOWN_TOOLS]           # 二次白名单
            plan.plan.extend(next_actions)

7. ctx_summary = tools.get_context_summary()
     把工具累计输出（depth 结果 shape、seg 命中数、3D 实例位置尺寸、距离/方位数字）
     格式化为文本

8. answer = Reflector.finalize(question, answer_format, ctx_summary, memory_ctx)
     最后一次 LLM 调用。基于全部工具证据 + Memory 上下文抽取符合格式
     （fill=数字、select=A/B/C/D）的最终答案。返回 AgentResult。
```

训练模式在此之后调用 `evolve_after_sample`（§ 3.7）；测试模式跳过。

### 3.2 底层工具集

SpatialMem 的空间感知能力来自 10 个底层工具，这些工具是**硬编码的确定性 Python 函数**，VLM 从不接触工具代码，只读其自然语言描述（`agent/tools.py::TOOL_DESCRIPTIONS`）。工具分两大类：A 类生成视觉/几何证据，B 类在几何证据上执行精确数值计算。

#### A 类：视觉生成工具（Visual Generation）

**1. `depth_estimation`** — 核心感知工具，是绝大多数下游工具的前提。调用 **DA3（Depth Anything 3）**[Lin et al. 2025, arXiv:2511.10647] 对样本全部帧（VSI-Train-10k 每场景 32 帧）做**单目度量深度估计**，同时输出每帧的相机内参矩阵（3×3）、世界坐标系到相机坐标系的外参矩阵（3×4），以及反投影得到的**全场景稠密 3D 点云**。DA3 在大规模多视图真值上训练，能产出度量尺度（米）而非相对尺度的深度，这是后续所有定量几何计算的基础。

**2. `bev_generation`** — 从 `depth_estimation` 产出的 3D 点云渲染**鸟瞰图**（Bird's-Eye-View，BEV），提供场景平面布局的直观视图。输出带真实米制坐标标注的 BEV 彩色图。

**3. `novel_view_synthesis`** — 使用 **3D 高斯溅射**（3DGS）从新视角渲染场景图像。支持 10 种相机运动方式（yaw/pitch/平移），用于探查被遮挡区域或验证特定空间关系。需要 `depth_estimation` 预先估计高斯初始化点云。

**4. `object_segmentation`** — 调用 **SAM3.1**（Segment Anything 3）对每帧独立做**文本提示分割**，返回每帧每个检测实例的二值掩码（H×W）、包围框（xyxy 像素坐标）和置信分数。同一次调用只处理一类物体，需要检测多类时多次调用。`object_category` 参数写入 `tools.context["seg_categories"]`，供后续 Memory 更新使用。

**5. `annotation_localization`** — 对含有 2D 标注标记（红点、蓝框等）的样本，将标记直接反投影到 3D，跳过 SAM3 分割。VSIBench/VSI-Train-10k 样本无标注，此工具在当前训练中几乎不启用。

#### B 类：计算执行工具（Code Execution）

**6. `instance_3d_localization`** — 核心几何工具。把 A 类工具产出的 2D 掩码通过深度图和相机位姿**反投影到 3D 空间**，为每个检测实例计算 3D 质心和轴对齐包围框（世界坐标系，单位米）。跨帧**聚类合并**：同类别、3D 包围框有重叠的检测视为同一物理实例，赋全局 instance ID。输出 `obj_id_list`、`merged_positions`、`merged_bbox_size`、`merged_scores`、`merged_labels`，是 #7/#8/#9 三个数值计算工具的共同上游。

**7. `distance_computation`** — 在 `instance_3d_localization` 结果上计算度量距离（米），支持两种模式：
  - `object_to_object`：两物体 3D 包围框之间的**最近点距离**，严格匹配 VSIBench 题干"Measuring from the closest point of each object"的语义。
  - `object_to_camera`：物体质心到指定帧相机光心的距离。

**8. `direction_computation`** — 计算从**观察者视角**看，目标物体相对于参考物体的**相对方向**。在水平面投影后给出方向标签（front/back/left/right 及组合）和角度偏移。支持三层灵活参数：`viewpoint`（观察者位置，可以是物体或相机）、`reference`（方向参考锚点）、`facing`（可选：显式指定观察者朝向的物体，解决 viewpoint==reference 时前向不定义的歧义）。这是方向推理题中最容易出错的工具，对应 SKILL `judge_direction` 的主要封装对象。

**9. `instance_counting`** — 对 `instance_3d_localization` 产出的全局实例列表计数，返回唯一实例总数及 ID 列表。

**10. `scene_size_computation`** — 从 `depth_estimation` 产出的 3D 点云（过滤低置信度和离群点后）估计**整体场景包围盒**（宽/高/深，米）和**地板面积**（平方米）。结果同时写入 `tools.context["scene_size"]`，可被 Path A/B 的 `_update_memory_from_tools` 提取，更新 `scene_scale_priors.json`。

#### 工具依赖图

```
depth_estimation ──────────────────────────── bev_generation
       │                                       novel_view_synthesis
       │                                       scene_size_computation
       │                                       annotation_localization
       │
       └─── object_segmentation ────────── instance_3d_localization ─── distance_computation
                                                                     ├── direction_computation
                                                                     └── instance_counting
```

`depth_estimation` 是几乎所有下游工具的必要前驱（annotation_localization 也依赖它做反投影）；`object_segmentation` 独立于 depth（可先跑分割）但其结果须等 `instance_3d_localization` 才能用于数值计算。典型的最短工具链为 `depth → seg → 3d_loc → {dist|dir|count}`，对应 4 个种子 SKILL 的 Tool Sequence。

#### 两个底层感知模型

| 模型 | 用途 | 工具映射 |
|---|---|---|
| **DA3 (Depth Anything 3)** arXiv:2511.10647 | 单目度量深度估计 + 相机位姿 + 3DGS | `depth_estimation`、`bev_generation`、`novel_view_synthesis` |
| **SAM3.1** (Segment Anything 3.1 Multiplex) | 文本提示目标检测与分割 | `object_segmentation` |

这两个模型是唯一直接消费 GPU 的组件；B 类工具（`distance_computation` 等）均为纯 NumPy/Python 几何计算，在 CPU 上完成。

### 3.3 Memory：三种数据 + 一个附属缓冲

**类接口** `agent/memory.py::Memory`。构造时确保下列文件存在于 `memory/` 目录：

**① `object_size_priors.json` — 物体尺寸先验**

- 写入接口：`update_object_size_prior(name, width=, height=, depth=)`
- 读取接口：`get_object_size_prior(name)`

结构：
```json
{
  "schema_version": "1.0",
  "objects":    { "chair":    {"width": {...}, "height": {...}, "depth": {...}} },
  "candidates": { "monitor":  {"width": {...}, ...} }
}
```

每个维度存 Welford 在线统计 `{count, mean, M2, std}`，更新公式（见 `_update_prior`）：

$$
n \leftarrow n+1,\quad
\delta = x - \mu,\quad
\mu \leftarrow \mu + \delta/n,\quad
M_2 \leftarrow M_2 + \delta(x-\mu),\quad
\sigma = \sqrt{M_2/n}
$$

二级池机制：`count < WARMUP_N=5` 的新条目暂存 `candidates` 池，某维 count 达阈值后**整条**升入 `objects` 主池。此机制防止个别异常观测污染主先验。

**② `scene_scale_priors.json` — 场景尺度先验**

- 写入接口：`update_scene_scale_prior(scene_type, width=, height=, depth=, floor_area=)`
- 读取接口：`get_scene_scale_prior(scene_type)`

结构和物体尺寸对称，但 key 是**Planner 每次显式输出的 `scene_type` 字段**（`bedroom` / `kitchen` / `office` 等），维度包含 `floor_area`。

**③ `unsolved_cases.jsonl` — 疑难样本记录**

- 写入接口：`record_unsolved(sample_id, task_type, predicted, gt, reason, trajectory_summary)`
- Append-only

每行一条 JSON：

```json
{ "ts": 1782, "sample_id": "4734", "task_type": "object_abs_distance",
  "predicted": "0.9", "gt": "2.2",
  "reason": "reconstruct verification failed",
  "trajectory": { "chosen_skill": "measure_distance", "tool_calls": [...] } }
```

`trajectory` 里包含 `chosen_skill` 字段 —— Memory **直接引用了 SKILL**。这是 § 3.5 讨论的交叉点之一。

**④ `memory/category_trajectories/{task_category}.jsonl` — 类别未覆盖轨迹缓冲**

**物理上放在 memory/ 目录下，但不由 `Memory` 类管理**，而是由 `agent/evolve.py::_log_uncovered_category` 直接读写。当 `Planner.chosen_skill == null`（即当前样本没有 SKILL 匹配）时，把整条轨迹追加到对应类别的日志。

此缓冲专为**类别级 bootstrap** 服务：当某类别累积到 `BOOTSTRAP_TRIGGER_N=8` 条无 SKILL 轨迹时，`bootstrap_skill_for_category` 读**全部**这些轨迹，综合分析后主动设计一个 SKILL 存到 pending 池。

**Memory 的整合读取接口** `Memory.format_context(task_category, object_names, scene_type)`：

- 输入 `object_names`（Planner 从问题里提取的物体名列表）→ 查 `object_size_priors`
- 输入 `scene_type`（Planner 推断的场景类型）→ 查 `scene_scale_priors`
- 输出形如：

```
[Size Priors]
  chair: width=0.48±0.08m, height=0.86±0.12m, depth=0.52±0.10m
  table: width=1.20±0.30m, height=0.75±0.05m

[Scene Scale Prior — bedroom]
  floor_area=18.50m², width=4.50m, height=2.65m
```

无匹配时返回字面量 `"No relevant memory found."`，让 LLM 明确知道无先验可用（避免瞎编）。

### 3.4 SKILL：文件夹级可执行知识单位

**类接口** `agent/skill_lib.py::SkillLib`（管理主库）、`Skill` dataclass（单个 SKILL 的运行时表示）。

**每个 SKILL 是一个文件夹**，形如 `skills/measure_distance/`，包含且仅包含 3 个文件：

#### ① `SKILL.md` — 描述性文档

YAML frontmatter + 5 段 Markdown：

```markdown
---
name: measure_distance                # SKILL 唯一标识
task_categories: [distance]           # 该 SKILL 覆盖的 task category（决定检索命中）
total_calls: 12                       # 累计调用次数（record_call 更新）
success_count: 8                      # 成功次数（用于 pending → main 晋升判定）
failure_count: 4
success_rate: 0.6667                  # = success_count / total_calls
version: 3                            # 结构性变更次数（append_pitfall / rewrite 触发）
seeded: true                          # 是否为手写种子；false 表示由 Path B/D 或 Bootstrap 蒸馏产出
---

# When to Use
两物体距离测量或物体到相机距离。Path A 每 DISTILL_TRIGGER_N=5 次成功后可被 LLM 重写。

# Parameters
- `targets` (list[str], REQUIRED): 至少 2 个物体名
- `mode` (str): "object_to_object" | "object_to_camera"
- ...

# Tool Sequence
1. depth_estimation
2. object_segmentation × N
3. instance_3d_localization
4. distance_computation

# Known Pitfalls        # ← Path C 追加（append_pitfall）
- **[反射材质]** 玻璃/镜面导致深度失效 → 改用 3D 重建
- ...

# Examples
...
```

前 4 段（`When to Use`、`Parameters`、`Tool Sequence`、`Known Pitfalls`）都会被自进化机制读写。

#### ② `execute.py` — 可执行函数

签名固定：

```python
def execute(sample, tools, ctx, params=None) -> dict:
    """
    输入：
      sample : SpatialSample
      tools  : ToolRegistry — 用 tools.execute_tool(name, params, frame_paths) 调
      ctx    : 共享上下文 — 读 ctx["frame_paths"] 拿准备好的帧
      params : Planner 输出的 skill_params 字典
    输出：
      { "success": bool, "tool_calls": list[dict], "summary": str }
    """
```

被 `SkillLib.invoke` 通过 `importlib.util` 动态加载调用。种子 SKILL 的 `execute.py` 由人手写；进化产出的 SKILL 由 LLM 撰写并经过 **AST 语法校验 + runtime import 校验** 才落到 `skills/pending/`。

#### ③ `trajectories.jsonl` — Append-only 调用日志

每次 `SkillLib.record_call(skill_name, success, trajectory_summary)` 追加一行：

```json
{ "ts": 1782, "success": true, "sample_id": "4946",
  "task_type": "object_abs_distance", "task_category": "distance",
  "chosen_skill": "measure_distance",
  "skill_params": {"targets": ["door", "refrigerator"], "mode": "object_to_object"},
  "tool_calls": [{"tool_name": "depth_estimation", "success": true}, ...] }
```

Path A 的 `distill_success` 读该文件的近 `DISTILL_WINDOW=20` 条，让 LLM 综合分析后重写 `When to Use`。

**主库 vs pending 池**：`skills/*/`（主库）与 `skills/pending/*/`（待晋升池）目录并列。`SkillLib.retrieve(task_category, top_k=3, include_pending=True)` 同时检索两者。Pending SKILL 被 Planner 选中并成功执行 `PENDING_PROMOTE_K=3` 次后，`promote_from_pending` 将其整目录 `mv` 到主库。

**SKILL 的语义地位**：SKILL 是**"某类任务的最小可复用解决方案单元"**。它比工具（tool）粗一层 —— 工具是原子的确定性计算（`depth_estimation` 直接跑 DA3），SKILL 是工具的**参数化组合模式**（`measure_distance` 描述"depth → seg × N → 3d_loc → dist"并封装其调用逻辑）。**SKILL 是 Planner 直接选择的对象**；工具是 SKILL 内部或 Reasoner 循环内部调用的对象。

### 3.5 SKILL 与 Memory：独立特征 + 相互联系

我们**不将 SKILL 与 Memory 描述为完全割裂的两块知识库**，但也**不模糊两者的边界**。它们**各有独立特征使其无法互相替代**，同时在训练循环中**通过 4 个具体位置协作**。

#### 3.5.1 独立特征对比 —— 两者不可互换

|  | **SKILL**（过程性、主动调用） | **Memory**（陈述性、被动查询） |
|---|---|---|
| **存储形式** | 文件夹（.md + .py + .jsonl） | JSON + JSONL |
| **核心内容** | **可执行 Python 代码** + 使用文档 | **数值统计** + 事实记录 |
| **代码上的载体** | `agent/skill_lib.py::Skill` dataclass | `agent/memory.py::Memory` 类 |
| **迭代术语** | **进化（evolve）** | **更新（update）** |
| **迭代方式** | 结构性变化：新草案生成、pending 晋升、版本号 bump、段落改写 | 单调量变：Welford 均值方差累加、条目追加 |
| **消费方式** | **主动调用**：`SkillLib.invoke(skill, ...)` 触发 `execute.py` 里的 tool 序列 | **被动查询**：`Memory.format_context(...)` 拼进 LLM 上下文供参考 |
| **对 Planner 决策的贡献** | 提供**动作**（选中它就代表选中一套确定的工具执行方案） | 提供**先验**（用于生成/校验答案的合理性） |
| **写入触发** | Path A/B/C/D、Bootstrap（5 种进化机制） | Path A/B 中的 `_update_memory_from_tools`；Path C/D 失败后 `record_unsolved`；每次无 SKILL 样本的 `_log_uncovered_category` |
| **检索/查询接口** | `SkillLib.retrieve(task_category, top_k=3)` 按类别匹配 + 成功率排序 | `Memory.format_context(task_category, object_names, scene_type)` 按物体名/场景名查先验 |
| **失败保护机制** | AST 校验 + runtime import 校验 + pending 池隔离 | 二级池（candidates → main）+ WARMUP_N 阈值 + 词数过滤（防长短语污染） |
| **独有内容（Memory 里没有）** | `execute.py` 可执行代码、`Known Pitfalls` 过程级教训、tool_sequence、parameters schema、version 号 | — |
| **独有内容（SKILL 里没有）** | — | 物体尺寸的 Welford 均值方差、场景尺度先验、疑难样本清单、类别未覆盖轨迹缓冲 |

**互不可替代的具体理由**：

- **SKILL 里没有"物体一般多大"这种数值先验** —— 硬要塞到 SKILL.md 里就变成了非结构化文本，无法数值校准。
- **Memory 里没有"某类问题的最优工具序列"** —— 硬要塞成 JSON 字段就变成了不可执行的文本描述，无法直接触发。
- 二者存储和消费方式不同：`SkillLib.invoke` 需要一个 Python 函数对象，`Memory.format_context` 需要拼进 prompt 的纯文本。**存储格式必须差异化才能各自服务好自己的消费路径**。

#### 3.5.2 相互联系 —— 4 个协作位置

尽管特征独立，SKILL 与 Memory 在训练循环中通过 4 个具体位置**协作**（每处都能指到代码行）：

**联系 1：Planner 消费两者，联合决策**（`Orchestrator.run` 步骤 2-4）

```python
memory_ctx = self.memory.format_context(task_category, object_names, ...)   # 陈述性
retrieved  = self.skill_lib.retrieve(task_category, top_k=3)                 # 过程性
plan       = self.planner.plan(sample, memory_ctx, retrieved, tool_descriptions)
```

Memory 提供**"这类物体大概多大"**，SKILL 提供**"这类问题以前怎么解"**。两者作为 Planner prompt 的两个独立段落联合参与决策。**读方向的联合。**

**联系 2：SKILL 决策反向精细化 Memory 上下文**（`Orchestrator.run` 步骤 5）

```python
scene_type = plan.get("scene_type") or ""   # Planner 决策的一部分
if scene_type:
    memory_ctx = self.memory.format_context(  # 用 scene_type 重组 memory 上下文
        task_category, object_names, scene_type=scene_type)
```

Planner 输出的 `scene_type` 让 Reflector.finalize 能查到该场景的尺度先验做合理性校验。**决策反哺检索。**

**联系 3：工具输出通过 evolve 双向分流**（`agent/evolve.py::_update_memory_from_tools`）

```python
def _update_memory_from_tools(ctx, memory, sample, updates):
    r3d = ctx.get("results_3d")   # SKILL 或 raw-tool 循环调 instance_3d_localization 的输出
    for i in r3d["obj_id_list"]:
        obj_name = seg_categories.get(labels[i], ...).strip().lower()
        if valid(obj_name):
            memory.update_object_size_prior(obj_name, width=..., height=..., depth=...)
    # 同时，evolve 的其他分支把该次调用摘要追加到对应 SKILL 的 trajectories.jsonl
```

一次工具执行**同时**更新 Memory 的数值先验（陈述性投影）和 SKILL 的调用历史（过程性投影）。**写方向的双分流。**

**联系 4：Memory 缓冲区是 SKILL 的原料**（`_log_uncovered_category` → `bootstrap_skill_for_category`）

```python
if not result.chosen_skill:
    _log_uncovered_category(sample, result, memory.root / "category_trajectories")
    # 当 {cat}.jsonl 累积 ≥ BOOTSTRAP_TRIGGER_N=8 条：
    bootstrap_skill_for_category(cat, trajs, llm, skill_lib)
    # LLM 读全部 trajs → 生成新 SKILL → save_pending
```

Memory 中的失败经验（作为原料）**被消化成过程性技能**（新 SKILL 落 pending）。**跨类型转换。**

#### 3.5.3 一个直观类比

若把 SpatialMem 视为一位空间推理"专业医生"，那么：

- **Memory 类比诊断参考资料**：正常值范围（物体典型尺寸、房间典型面积）、既往疑难病例（unsolved_cases）、未归类观察日志（category_trajectories）。医生**看这些做参考、做校验**，但不直接"执行"它们。
- **SKILL 类比标准操作规程（SOP）**：某类问题的完整手术流程（Tool Sequence）、注意事项（Known Pitfalls）、参数模板（Parameters）。医生**直接照做**，不需要每次现推。

Memory 用来**校验**："这个测量结果合理吗，跟先验差多少？"
SKILL 用来**执行**："这类问题按这套流程办就行。"

两者**共同源自同一学习过程**（每次案例的经验），但**按用途分派到两种不同的载体**。诊断资料不会突然变成 SOP，SOP 也不会退化成参考数值 —— 但它们互相引用（SOP 里可能提到"参照 X 手册的正常值"，参考资料里可能记"手术 X 有 3% 并发症率"）。这正好对应 § 3.5.1 的独立特征 + § 3.5.2 的协作位置。

### 3.6 三个 LLM 角色

**Planner**（`agent/planner.py`）—— 全局决策者。看到问题、图像（downsample 后前 3 帧）、Memory 上下文、SKILL brief 列表、10 个工具的完整描述。输出 plan JSON：

```json
{
  "task_category": "distance" | "counting" | ...,
  "scene_type": "bedroom" | "kitchen" | null,
  "analysis": "1-3 句：问题问什么，需要什么证据",
  "object_targets": ["chair"],
  "chosen_skill": "measure_distance" | null,   // 严格限制在 retrieved 名字里
  "skill_params": {...},                        // 从 SKILL.md Parameters 段读格式
  "plan": [{"step": 1, "tool": "...", ...}]   // 仅当 chosen_skill == null 时用
}
```

关键 prompt 约束：`chosen_skill` 只能是检索列表里存在的 SKILL 名，**不能是工具名**（Orchestrator 会二次校验并回退）。

**Reasoner**（`agent/reasoner.py`）—— 局部工具选择器。**仅当 Planner 未选 SKILL 时启用**，在 `_raw_tool_loop` 中细化 plan 的每一步。输出：

```json
{ "tool": "one_of_10_KNOWN_TOOLS", "params": {...}, "reasoning": "..." }
```

Orchestrator 层强制检查 `tool ∈ KNOWN_TOOLS`（10 个工具白名单）；不在则回退到 plan 原步骤。此约束防止 LLM 幻觉工具名（例如 `first_appearance_analysis`）。

**Reflector**（`agent/reflector.py`）—— 三合一，三个函数各一套 prompt：

- `reflect(question, plan, ctx_summary, failure_patterns)`：`_raw_tool_loop` 每轮末尾调用。输出 `{confidence, decision: continue|terminate, next_actions: [...]}`。若 decision=continue，next_actions 里的工具名也被 KNOWN_TOOLS 二次过滤。
- `reconstruct(sample, plan, predicted, ctx_summary, tool_descriptions)`：**仅训练时答错触发**。看 GT vs predicted vs plan vs ctx，输出 `{diagnosis, corrected_plan}`。corrected_plan 供 `Orchestrator.run_with_plan` 重跑验证用。这里的 max_tokens 设为 6144（比默认 4096 高，因为 corrected_plan 通常较长）。
- `finalize(question, answer_format, ctx_summary, memory_ctx)`：单样本推理的**最后一次 LLM 调用**。从全部工具证据抽取符合格式的答案。此处 Memory 的尺度先验通过 `memory_ctx` 传入，被用于**合理性校验**（若计算出的物体尺寸远超先验则降低置信度）。

### 3.7 五种自进化机制

训练时 `TrainLoop.run_single(sample, evolve=True)` 在 `Orchestrator.run` 之后调用：

```python
evolve_after_sample(result, sample, memory, skill_lib, reflector, orchestrator,
                    llm, evaluate_answer)
```

根据 `(result.success, result.chosen_skill != null)` 分派：

#### Path A — 答对 + 用了 SKILL $\sigma$

```
1. skill_lib.record_call(σ, success=True, trajectory_summary)
     ↳ σ.total_calls++, σ.success_count++, success_rate 重算，写回 SKILL.md frontmatter
     ↳ trajectory_summary 追加到 σ 目录下的 trajectories.jsonl

2. if σ.success_count % DISTILL_TRIGGER_N == 0:
     distill_success(σ, skill_lib, llm)
       ↳ 读 σ 的 trajectories.jsonl 近 DISTILL_WINDOW=20 条
       ↳ LLM 输出 {when_to_use: "...", changed: bool, rationale: "..."}
       ↳ 若 changed=true: skill_lib.rewrite_section(σ, "When to Use", new_text)
                          skill_lib.bump_version(σ)

3. _update_memory_from_tools(orchestrator.tools.context, memory, sample, updates)
     ↳ 从 tools.context["results_3d"] 提物体尺寸 → memory.update_object_size_prior
     ↳ 从 tools.context["scene_size"] 提场景尺度 → memory.update_scene_scale_prior
```

#### Path B — 答对 + 没用 SKILL

```
1. if len(successful_tool_calls(traj)) >= 2:
     distill_new_skill(sample, trajectory, llm, skill_lib)
       ↳ 先检索该 task_category 下所有已有 SKILL（主库 + pending），展示给 LLM
       ↳ LLM 输出三种 action 之一：
           {"action": "skip"}                          # 已有 SKILL 已覆盖，不新建
           {"action": "update", "name": "...",         # 已有 SKILL 相似，追加描述
            "append_when_to_use": "..."}
           {"action": "create", "name": "...",         # 真正不同的新策略
            task_categories, when_to_use, parameters,
            tool_sequence, execute_py_body}
       ↳ update → skill_lib.rewrite_section 追加 When to Use + bump_version
       ↳ create → ast.parse + execute() 存在检查 + runtime import 校验
               → skill_lib.save_pending(name, md, py) 落到 skills/pending/{name}/
               → 三关都过 → 返回 name；否则删除并返回 None
2. _update_memory_from_tools(...)   # 同 Path A
```

#### Path C — 答错 + 用了 SKILL $\sigma$

```
1. skill_lib.record_call(σ, success=False, trajectory_summary)

2. corrected = _reflect_and_verify(sample, result, reflector, orchestrator,
                                    evaluate_answer, tool_descriptions):
     for attempt in range(REFLECT_MAX_ATTEMPTS=1):
       rc = reflector.reconstruct(sample, result.plan, result.predicted,
                                   result.final_context, tool_descriptions)
       if not rc.corrected_plan: return None
       verify = orchestrator.run_with_plan(sample, rc.corrected_plan)
                # ↑ 关键：用同一样本重跑修正 plan
       verify.success = evaluate_answer(verify.predicted, sample.gt_answer, ...)
       if verify.success:
         return (rc.corrected_plan, verify, True)
     return None

3. if corrected is not None:
     pitfall = distill_pitfall(fail_result=result, corrected_result=verify, llm)
       ↳ LLM 对比失败/成功的两次执行 → 输出 {pitfall: "**[trigger]** ... → ...",
                                              is_new: bool, rationale: "..."}
       ↳ if is_new: skill_lib.append_pitfall(σ, pitfall)
                    skill_lib.bump_version(σ)
   else:
     memory.record_unsolved(sample.id, task_type, predicted, gt,
                            reason="reconstruct verification failed",
                            trajectory_summary=...)
```

#### Path D — 答错 + 没用 SKILL

同 Path C 的 verify 流程；若 verify 通过，走 Path B 的 `distill_new_skill`（用修正轨迹作输入）蒸馏新 SKILL 到 pending；不通过则 `record_unsolved`。

#### Bootstrap — 类别级主动机制（Path B/D 之外的独立入口）

```
if not result.chosen_skill:
    _log_uncovered_category(sample, result, memory.root / "category_trajectories")
    # 无论对错，追加到 memory/category_trajectories/{task_category}.jsonl

    _maybe_bootstrap_category(task_category, skill_lib, memory, llm):
      marker = memory/category_trajectories/{cat}.bootstrapped
      if marker.exists(): return None                             # 只做一次
      if skill_lib.retrieve(cat, top_k=1, include_pending=True): return None
                                                                   # 已有 SKILL 就不 boot
      trajs = read all of {cat}.jsonl
      if len(trajs) < BOOTSTRAP_TRIGGER_N=8: return None

      bootstrap_skill_for_category(cat, trajs, llm, skill_lib):
        correct = [t for t in trajs if t.success]
        wrong   = [t for t in trajs if not t.success]
        ↳ LLM 读 correct[-5:] + wrong[-5:] 对比分析
        ↳ 输出 {name, task_categories, when_to_use, parameters,
                 tool_sequence, execute_py_body}
        ↳ 同 distill_new_skill 一样做 AST + runtime 校验
        ↳ 通过则 skill_lib.save_pending(name, md, py)
      marker.touch()                # 无论成功失败都标记，避免反复重试
```

**Path B 优先于 Bootstrap**：若某样本触发 Path B 并成功蒸馏出 pending SKILL，后续 bootstrap 检查 `retrieve()` 会返回非空 → 跳过 bootstrap。这防止两条路径重复生成同类 SKILL。

### 3.8 反思—重跑验证—蒸馏闭环（Path C/D 的核心保障）

`agent/evolve.py::_reflect_and_verify` 是 Path C/D 与"直接 LLM 反思"的关键区别。规则：

$$
\text{persist}(\text{update to } \sigma) \iff \exists\ \pi'\ \text{使得}\ \text{Orchestrator.run\_with\_plan}(s, \pi').\text{answer} = a^\star(s)
$$

$\pi'$ 是 Reflector.reconstruct 提出的修正 plan。只有当**用 $\pi'$ 在同一样本 $s$ 上重跑，产出的答案与真值 $a^\star(s)$ 匹配**，才把这条反思蒸馏为持久知识（Path C 的 pitfall 追加或 Path D 的新 SKILL）。

这与 Reflexion 类工作的差异：Reflexion 把反思文本直接追加到 prompt 作为下轮上下文，不做实际验证；SpatialMem 要求反思变成具体的修正 plan、并在真样本上跑通、且答案匹配 GT，才允许写入 SKILL 库。

**代价**：每次 Path C/D 多一次 `run_with_plan`（含相关工具子集调用 + 一次 Reflector.finalize），约 +30% 计算量。
**收益**：Known Pitfalls 里的每条教训都是"验证过在真实样本上确有其事"的教训，不受 LLM 幻觉污染。

若验证不通过，样本走 `memory.record_unsolved` 落到 `unsolved_cases.jsonl`。SKILL 库不受任何写入，保持干净。

### 3.9 pending 池的检索、复用与晋升

新蒸馏的 SKILL（Path B/D 或 Bootstrap 产出）先落 `skills/pending/`。`SkillLib.retrieve(include_pending=True)`（默认开启）与主库一起检索到，附 `[AUTO-DISTILLED — 系统自动总结的策略，符合需求可直接使用]` 标签，鼓励 Planner 积极使用而非回避。

若 Planner 选中 pending SKILL，`SkillLib.get(name)` 在 `skills/` 和 `skills/pending/` 依次查找，`invoke` 通过 `_import_execute` 动态加载执行。执行完成后 `record_call` 更新 pending SKILL 的 frontmatter。

当 pending SKILL 的 `success_count >= PENDING_PROMOTE_K=3`，`train_vsitrain10k.py` 每 `PROMOTE_EVERY=50` 个样本调一次 `promote_eligible_pending`，将其目录整个 `mv` 到检查点下的 `skills/` 成为正式主库成员。

早期版本此机制曾因 `retrieve` 默认 `include_pending=False` 而形成死循环（pending 永远不被检索 → 永远无成功 → 永远不晋升）；现在 `include_pending=True` 是默认值，pending 池能够被有效消费。此外，训练时 SKILL/Memory 均写入检查点目录（`ckpts/<name>/`），而非项目根目录下的 `skills/`、`memory/`（只读 base）。

### 3.10 实现细节

**LLM 接口**（`agent/llm_client.py::LLMClient.chat_json`）：默认使用 OpenAI 兼容的 `response_format={"type": "json_object"}` 结构化输出模式，遇到端点不支持时自动回退到自由格式，并进行 3 次 JSON 解析重试。这大幅降低复杂 SKILL 蒸馏 prompt 上的 JSON 解析失败率。

**per-call max_tokens 调整**：
- 默认 `chat_json`：4096
- `Reflector.reconstruct`：6144（corrected_plan 可能较长）
- `distill_new_skill` / `bootstrap_skill_for_category`：8192 / 12288（输出含完整 execute.py 函数体）

**工具白名单**（`agent/orchestrator.py::KNOWN_TOOLS`）：Reasoner 与 Reflector.next_actions 的返回结果处硬校验工具名。未在白名单内的建议被丢弃，回退到 Planner 原计划工具。这防止 LLM 发明不存在的工具名浪费轮次。

**帧数**：VSIBench/VSI-Train-10k 每场景 32 帧，`MAX_FRAMES_PER_SAMPLE = 32`，全部送入工具。

**验证式蒸馏的失败弹性**：若 Reflector 的修正 plan 也在重跑时失败，不猜测、不惩罚，只记入 `unsolved_cases.jsonl`。这类样本可作为未来手动种子 SKILL 的候选素材。

**pending SKILL 的三重校验**（`distill_new_skill` / `bootstrap_skill_for_category`）：
1. AST 语法 parse 通过；
2. 语法树中存在 `def execute(...)`；
3. 用 `importlib.util` 实际加载模块无 runtime 错。
任一失败则删除 pending 目录，返回 None。这保证 SKILL 库中不存在"能保存但一调用就崩"的死代码。

### 3.11 什么是初始给定的，什么是训练时学出来的

为避免读者误以为 SpatialMem"完全从零 self-evolve"，我们明确分开**手工先验**与**进化产出**。所有分界线在代码中通过 SKILL.md frontmatter 的 `seeded` 字段与文件位置直接可查。

**手工先验（一次性 hand-craft，训练开始前就存在）**：

1. **10 个底层工具的实现**（`agent/tools.py::ToolRegistry` 及 `tools/*/*.py`）：`depth_estimation`, `object_segmentation`, `instance_3d_localization` 等，均为确定性 Python 函数，包裹 DA3、SAM3、几何计算等模块。VLM **从不接触工具代码**，只读工具的文字描述。
2. **10 个工具的自然语言描述**（`agent/tools.py::TOOL_DESCRIPTIONS`）：约 2000 词的 hand-crafted 文本，说明每个工具的输入/输出/依赖/典型用法。此描述被拼进 Planner 和 Reasoner 的 prompt。
3. **3 个角色的 prompt 模板**（`agent/planner.py`, `reasoner.py`, `reflector.py`）：包含决策规则、JSON 输出格式规范、SKILL 与 tool 的区分约束、KNOWN_TOOLS 白名单等。
4. **4 个种子 SKILL**（`skills/{measure_distance, count_objects, judge_direction, measure_scene_size}/`）：hand-craft 的 SKILL.md（约 20 行描述）+ hand-craft 的 execute.py（约 30 行调用逻辑）。frontmatter 标记 `seeded: true`。每个种子对应 VSIBench 10 类中的一类。**其余 6 类无手写 SKILL**，完全靠训练时进化产出。
5. **8 个进化超参**（`agent/config.py`）：`WARMUP_N=5`, `DISTILL_TRIGGER_N=5`, `PENDING_PROMOTE_K=3`, `BOOTSTRAP_TRIGGER_N=8` 等。

**训练时进化产出**：

1. **新 SKILL**：Path B（单次成功蒸馏）、Path D（反思成功蒸馏）、Bootstrap（类别级综合）三条路径产出的 pending SKILL 及其晋升到主库的正式 SKILL。全部 `seeded: false`。
2. **SKILL 内部的段落更新**：
   - `When to Use` 段落被 Path A 的 `distill_success` 定期重写；
   - `Known Pitfalls` 段落被 Path C 的 `distill_pitfall` 追加；
   - `version` 字段随每次结构性更新递增。
3. **SKILL 的运行统计**：`total_calls`, `success_count`, `failure_count`, `success_rate` 每次 `record_call` 更新。
4. **Memory 数值先验**：`object_size_priors.json` 与 `scene_scale_priors.json` 的 Welford 均值方差、条目从 candidates 到 objects 的晋升。
5. **Memory 疑难样本记录**：`unsolved_cases.jsonl` 与 `category_trajectories/*.jsonl` 的累积。

**为什么这一分界重要**：论文的核心贡献不是"零知识起步"（那样的智能体不切实际），而是"从少量手工先验出发，通过训练时反馈持续扩充知识库"。我们把手工先验限制在 4 个种子 SKILL + 工具描述 + prompt 模板，进化机制负责把库从 4 个种子扩充到覆盖全部 10 类问题，并在每一类内部持续精化。

**驱动 VLM 需要"学"什么？** VLM 本身**不学工具的原子用法**（工具是硬编码 Python）。它只需要做两件事，这两件预训练时已经会：
- 看着工具/SKILL 的文字描述，输出正确的 JSON（选名字、填参数）。
- 基于问题和累积证据做多步推理决策。

真正需要"学习"的是**跨工具的高阶决策模式**——某类空间问题该用哪几个工具、按什么顺序、怎么组合。这才是 SKILL 库的价值：**把此类高阶模式从"每次靠 LLM 通用推理猜出"固化为"直接调用的可复用单元"**。4 个 seed SKILL 是 4 种典型模式的起手示范，进化路径负责发现其余的模式。

## 4 讨论

### 4.1 与 S-Agent 的关系

S-Agent 与 SpatialMem 都采用 Planner-工具-记忆架构，但记忆的**语义完全不同**：S-Agent 的 Scene/Agent 记忆记录**当前场景/当前推理会话**的中间状态（object grounding、tool observations），跨帧但不跨样本；SpatialMem 的 SKILL 与 Memory 记录**跨样本可复用的过程与先验**。这两类记忆是正交且互补的 —— 一个 SpatialMem 实例内部可以同时借用 S-Agent 风格的场景记忆作为 per-episode 的中间状态。

### 4.2 与 SpatialClaw 的关系

SpatialClaw 的核心贡献是**代码即动作接口**：VLM 直接写 Python 而非填 JSON schema。SpatialMem 主要使用结构化工具调用（因为 SKILL.md 描述的接口本就是结构化的），但 SKILL 的 `execute.py` 本质上也是代码 —— 可视为一种**中层代码化**。SpatialClaw 强调**单样本内的灵活组合**；SpatialMem 强调**跨样本的模式固化**。二者互补而非替代。

### 4.3 与 Voyager / SkillWeaver / MUSE-Autoskill 的关系

这些工作是 SpatialMem 在其它领域（Minecraft/Web/软件）的直系前身。SpatialMem 的独特之处：

1. **验证式蒸馏闭环**：只有真跑通的反思才蒸馏。Voyager 和 SkillWeaver 更依赖 self-verification（LLM 自己判断结果），可能引入幻觉；SpatialMem 在同一样本上实际重跑，抓的是 GT 差异。
2. **双通道 SKILL 发现**：Voyager 依赖自动课程逐步暴露新任务（reactive）；SpatialMem 加入 category 级 bootstrap，主动对累积失败类别设计 SKILL。
3. **SKILL 与 Memory 的关系不是割裂**：我们在 § 3.5 明确讨论了两者在 Planner 消费入口、evolve 写入路径、bootstrap 转换通道等 4 个位置的协作，而非简单声称"两者严格分离"。

### 4.4 假设的局限

**工具能力上界**。SpatialMem 的表现受底层工具集覆盖能力约束。对于 `route_planning`（多步导航决策）这类超出 10 个工具语义的任务，即使 bootstrap 触发，LLM 也未必能设计出有效 SKILL。这是一个**诚实的边界** —— 我们不宣称覆盖所有空间推理任务。

**幻觉污染的残余风险**。验证闭环大幅降低幻觉进入 SKILL 库的概率，但不为零：若某次修正 plan 的验证"恰好"因为工具输出的随机性通过，蒸馏出的 pitfall 可能是伪相关。可通过更严格的多轮验证（`REFLECT_MAX_ATTEMPTS > 1`）进一步压低这一风险。

**训练-测试分布迁移**。若测试集与训练集在 task_category 分布、物体类别分布上差异过大，SKILL 库积累的先验可能失配。我们计划在 MMSI-Bench 与 EmbSpatial 的交叉设置下评测这一鲁棒性。

## 5 计划的实验

**评测数据集**：

- **VSIBench** [Yang et al. 2025]：5130 条样本，10 种问题类型（距离/计数/方位/场景尺寸/物体尺寸/路径规划/时序等），主评测集。
- **MMSI-Bench** [Yang et al. 2025]：多图空间推理，测跨视角证据整合。
- **ViewSpatial-Bench** [Li et al. 2025]：视角感知定位。
- **EmbSpatial-Bench** [Du et al. 2024]：具身空间推理。
- **MindCube** [Wang et al. 2026]：从有限视角构建空间心智模型。
- **All-Angles-Bench**：多视角综合空间推理。

**基线**：
- 直接 VLM 推理（GPT-4o, GPT-5, Gemini 3 Pro, Claude Opus 4.7, Qwen3-VL 系列）
- S-Agent (arXiv 2606.20515)
- SpatialClaw (arXiv 2606.13673)
- 空间专用 VLM（Cambrian-S、Spatial-MLLM、VST 系列）

**主实验**：训练集积累 SKILL/Memory 后在各 bmk 上评测精度。**预期**：在 5+ 个 bmk 上超过 S-Agent 与 SpatialClaw，特别在需要跨样本经验的 category 上优势更大（如 distance、counting、direction_hard）。

**Ablation**（分解手工先验与进化机制各自的贡献）：

用户可能怀疑收益全来自 4 个手写种子而非自进化，我们通过下列 ablation 拆分：

| # | 设置 | 手工先验 | 进化机制 | 目的 |
|---|---|---|---|---|
| 0 | **Baseline** | 无 SKILL 检索 + 无 Memory 上下文，仅 raw-tool 循环 | 关 | 衡量 VLM+工具的原始能力 |
| 1 | **+Memory only** | Memory 数值先验（用于 Reflector 校验） | 关 | 陈述性知识的贡献 |
| 2 | **+seeded SKILLs** | 4 个手写种子 SKILL | 关 | **手工先验的总贡献**（"如果我们只是给 4 个 seed 不做自进化能到哪"） |
| 3 | +Path A only | 同 (2) | 只开 Path A | 强化 + When to Use 蒸馏的收益 |
| 4 | +Path B/D only | 同 (2) | 只开 Path B、D | 新 SKILL 蒸馏（反应式）的收益 |
| 5 | +Path C only | 同 (2) | 只开 Path C | Pitfall 追加的收益 |
| 6 | +Bootstrap only | 同 (2) | 只开 Bootstrap | 类别级主动生成的收益 |
| 7 | **Full** | 同 (2) | 全开 5 种机制 | **完整进化后的总能力** |

**关键对比**：**(7) − (2)** 是"自进化的净收益"—— 即从手工先验出发通过训练时反馈额外获得了多少精度。**(2) − (0)** 是"手工先验本身的贡献"，需要与净进化收益分开报告，才能诚实地展示"进化机制到底做了什么"。**(3)-(6) 分别拆解各条进化路径的独立收益**。

我们**预期 (7) − (2) 在覆盖了 seed 之外任务类别（`object_size_estimation`, `obj_appearance_order`, `route_planning` 等 6 类）上尤其显著**，因为这些类别的能力增益完全来自进化（Path B/D 或 Bootstrap 产出的新 SKILL）。

**驱动模型可迁移性**：分别用 GPT-4o-mini、Qwen3-VL-30B-A3B（≈8B 有效算力）、Qwen3-VL-235B-A22B、Gemini 3 Pro 驱动同一框架，验证架构对模型规模的鲁棒性。

**训练动态曲线**：随着训练样本数增长，观察 SKILL 库规模、SKILL 命中率、平均工具调用轮数、pending 池晋升数、per-category 精度的演化曲线，展示**"越训越好"** 的自进化特性。

---

## 6 结论

我们提出 SpatialMem —— 首个专为空间推理设计的**训练时自进化智能体框架**。其核心思想是把跨样本可复用的知识拆分为陈述性 Memory 与过程性 SKILL 库，通过五种自进化机制（Path A/B/C/D + 类别级 bootstrap）在训练集上不断积累和精化。反思—重跑验证—蒸馏的闭环保证知识入库的可信度。测试时 VLM 权重不改动，直接消费进化后的 SKILL 与 Memory。

我们相信这一范式补齐了 S-Agent（缺跨样本记忆）与 SpatialClaw（缺记忆）在空间推理智能体方向的关键空隙，并为空间智能体走向"越用越强"提供了具体路径。
